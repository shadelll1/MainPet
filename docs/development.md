# Разработка

Правила работы с исходниками и соглашения по коду проекта «Склад и продажи».

## Окружение

- 1С:Предприятие 8.3.27 (подходит учебная версия: исполняемый файл `1cv8t.exe`).
- Исходники — XML-выгрузка Конфигуратора в `src\`, формат `Hierarchical`, режим совместимости `Version8_3_27`.
- Файловая база — `base\` в корне проекта (в git не хранится).

## Цикл работы

```
load.bat   src -> база: создает базу, если ее нет, загружает конфигурацию, обновляет структуру БД
dump.bat   база -> src: выгрузка (инкрементальная, если есть src\ConfigDumpInfo.xml)
```

- Перед запуском скриптов Конфигуратор и 1С:Предприятие должны быть закрыты: учебная версия допускает один сеанс.
- Правки делаются либо в файлах `src\`, либо в Конфигураторе — не одновременно, иначе одна сторона затрет другую.
  После правок в Конфигураторе — `dump.bat`, после правок файлов — `load.bat`.
- Файлы — UTF-8 с BOM и переносами CRLF (так их пишет Конфигуратор). `.gitattributes` запрещает git их менять.
- `ConfigDumpInfo.xml` — служебный файл инкрементальной выгрузки; не редактировать, в git не хранится.
- Новый объект метаданных существует для платформы, только если он перечислен в `src\Configuration.xml` → `<ChildObjects>`.
- Формы создавать в Конфигураторе, затем `dump.bat`, и только потом править `Ext\Form\Module.bsl`.

## Проверки

Перед коммитом:

```
python3 tools/check_sources.py
```

Скрипт проверяет кодировку и переносы строк, корректность XML, число параметров `СтрШаблон`,
существование и экспортность вызываемых методов общих модулей и менеджеров, ссылки на метаданные в коде.
Эти же проверки и статический анализ BSL Language Server (`.bsl-language-server.json`) выполняются
в GitHub Actions на каждый push (`.github/workflows/checks.yml`); замечания уровня Error роняют сборку.

Главная проверка — `load.bat` без ошибок и зеленая самопроверка (Администрирование → «Запустить самопроверку»).

## Карта конфигурации

| Слой | Объекты |
|---|---|
| НСИ | `Номенклатура` (иерарх., артикул уникален), `Контрагенты` (иерарх., проверка ИНН/КПП), `Склады`, `ЕдиницыИзмерения`, `Пользователи` |
| Документы | `ПоступлениеТоваров`, `ПеремещениеТоваров`, `ЗаказКлиента`, `РеализацияТоваров` (ввод на основании заказа), `УстановкаЦенНоменклатуры` |
| Регистры накопления | `ТоварыНаСкладах`, `ПартииТоваров` (FIFO), `ТоварыВРезерве`, `ЗаказыКлиентов` — остатки; `Продажи` — обороты |
| Регистр сведений | `ЦеныНоменклатуры` (периодический, день, подчинен регистратору) |
| Логика | общие модули `ПроведениеСервер`, `ПартионныйУчетСервер`, `ЗаказыКлиентовСервер`, `ЦенообразованиеСервер` |
| Доступ | параметр сеанса `ТекущийПользователь` (модуль сеанса), RLS роли `Менеджер` по реквизиту `Ответственный` |
| Интеграция | HTTP-сервис `API` (`/api/v1/...`) → `ИнтеграцияAPIСервер` |
| Прочее | подписка `ПроверкаДатыЗапретаИзменения`, регламентные задания `ЗакрытиеПросроченныхЗаказов` и `ПересчетСебестоимости`, 3 отчета на СКД, 6 ролей |

## Соглашения по проведению

1. `ПроведениеСервер.ПодготовитьНаборыЗаписей(ЭтотОбъект)` — первой строкой `ОбработкаПроведения`.
2. Данные — запросом в менеджере документа (`ДанныеДляПроведения`), табличная часть **свернута** по ключам регистров, услуги отфильтрованы по `ТипНоменклатуры`.
3. Блокировки (`ПроведениеСервер.ЗаблокироватьСкладскиеОстатки`) — **до** чтения остатков.
4. Если остатки читаются на момент документа (FIFO, резерв) — `ПроведениеСервер.ОчиститьДвиженияВБазе` после блокировок.
5. Контролируемые регистры пишутся явно (`ПроведениеСервер.ЗаписатьДвижения`), затем контроль остатков **после записи**:
   `ПроведениеСервер.ПроверитьСвободныеОстатки`, `ЗаказыКлиентовСервер.ПроверитьОстаткиПоЗаказу`.
6. Документ, уменьшающий остаток при перепроведении или отмене проведения (поступление, перемещение), добавляет
   в контроль ключи старых движений: `ПроведениеСервер.КлючиДвиженийТоваровВБазе` — до перезаписи движений.
7. Документ, влияющий на партии, в `ПередЗаписью` вызывает `ПартионныйУчетСервер.ЗапомнитьДатуДоИзменения`,
   а в конце проведения и отмены проведения — `ПартионныйУчетСервер.ЗарегистрироватьИзменениеПартий`
   (сдвигает границу пересчета себестоимости, если документ проведен задним числом).
8. `ОбработкаПроверкиЗаполнения` вызывается только при интерактивной записи (из формы) или явным
   `ПроверитьЗаполнение()`. Программная запись ее не вызывает, поэтому инварианты, важные для любой
   записи (остатки, резервы, отгрузка по заказу), контролируются в проведении, а не в проверке заполнения.
9. Новый документ: реквизит `Ответственный` (заполняется `ОбщегоНазначения.ЗаполнитьОтветственного`),
   источник подписки `ПроверкаДатыЗапретаИзменения`, права в ролях.

## Правила по коду

- `СтрШаблон` поддерживает только `%1`–`%9`, и число значений должно совпадать с подстановками.
- `+` не приводит число к строке: `"Итого: " + Строка(5)`.
- Запросы — с параметрами, а не конкатенацией значений в текст.
- Экспортные методы — с комментарием: назначение, параметры, возвращаемое значение.
- Не создавать реквизит `Строка` длиной больше 1000 — для длинного текста неограниченная длина.

## Автотесты

Общий модуль `Самопроверка`: каждый тест — экспортная процедура `Тест_*`, зарегистрированная в `СписокТестов()`.
Тест выполняется в транзакции, которая всегда откатывается, поэтому создает свои данные и не оставляет следов.
Отказ проведения в негативном тесте — всегда последнее действие теста: после него транзакция испорчена.
